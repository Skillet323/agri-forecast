# Прогнозирование урожайности по данным погоды, почвы и спутника

Курсовой проект по дисциплине «Прогнозно-аналитические системы», профиль
«Управление данными». Тема выбрана самостоятельно: прогноз урожайности
на основе разнородных открытых источников — метеорологии, почвы, спутниковых
снимков и официальной статистики.

Прежде чем читать код, стоит понять, что в проекте два разных контура, и они
решают разные задачи.

**Контур по полям** (`pipeline.py`) — пять условных полей в Краснодарском крае,
один вегетационный сезон 2023 года. Здесь показан весь технический цикл: слои
хранения, инкрементальная загрузка, контроль качества, происхождение
показателей, история изменений, два дашборда. Урожайность в этом контуре
считается формулой-заглушкой (открытой статистики по отдельным полям не
существует), поэтому цифры отсюда годятся для демонстрации механики системы,
но не для содержательных выводов о реальном мире.

**Годовой контур** (`real_experiment.py`) — вся страна целиком, один год —
одно наблюдение, 2000–2023. Код сначала обращается к FAOSTAT/World Bank и NASA POWER,
а при недоступности источника переходит в предусмотренный `degraded_synthetic`
режим. Поэтому при защите необходимо смотреть статус сохранённого запуска в
`data/real_model_results.json` и не выдавать синтетический результат за официальную статистику.

Если коротко: контур по полям — это про архитектуру и требования методички,
годовой контур — про содержательный результат.

## Быстрый старт

```bash
pip install -r requirements.txt
python run_all.py
```

Соберётся всё: данные по полям, годовой ряд, обе модели, оба дашборда,
диаграммы для отчёта. Занимает минуту-две, сеть нужна для настоящих запросов
к NASA POWER, SoilGrids, World Bank и FAOSTAT — без сети или при недоступности
конкретного источника соответствующий шаг просто уйдёт в синтетику и в логе
будет явно на это указано.


Дашборд открывается прямо из файла: `data/dashboard.html`.

Для подготовки иллюстраций отчёта отдельно можно запустить:

```bash
python report_figures.py
```

Скрипт не выполняет сетевых запросов: карта полей, схемы конвейера, валидации,
контроль качества, lineage, историзация и статические представления дашбордов
строятся из уже сохранённых `config.py`, `warehouse.sqlite` и JSON-результатов.

## Структура

```

ingestion/
  nasa_power.py           погода, суточный REST API
  soilgrids.py             почва, REST API, обновляется годами
  sentinel2.py             NDVI (нужен OAuth Copernicus, пока не настроен — синтетика)
  faostat_yield.py         урожайность пшеницы по стране

  yield_bootstrap.py       формула-заглушка для контура по полям
```

## Как устроены обязательные части

**Источники.** Пять штук: NASA POWER (суточный JSON, без ключей), SoilGrids
(JSON, обновляется годами), Sentinel-2 (растры, нужен OAuth), FAOSTAT и
World Bank (годовая статистика). Различаются форматом, частотой обновления
и способом доступа — разнородность с запасом.

**Инкрементальная загрузка.** Таблица `load_state` хранит, докуда уже
загружено каждое поле по каждому источнику. Второй запуск подряд не лезет
в сеть за тем, что уже есть — в логе это видно как статус
`skipped_up_to_date`. Проверяется тестами в `tests/test_pipeline.py`.

**Идемпотентность.** Запись — `INSERT OR REPLACE` по первичному ключу.
Отдельно стоит урожайность: она обновляется через `UPDATE`, а не вместе
с остальными колонками, потому что `REPLACE` меняет строку целиком и на
инкрементальном запуске стёр бы погоду в уже загруженных днях. Ловили этот
баг на себе, тест `test_yield_survives_incremental_run` следит, чтобы он не
вернулся.

**Устойчивость к сбоям.** У каждого источника один и тот же контракт:
`fetch_real()` бросает исключение при сбое, `fetch()` его ловит и подставляет
синтетику с той же структурой данных, а не роняет весь конвейер. Для
урожайности в годовом контуре цепочка длиннее: FAOSTAT → World Bank →
синтетика. Это не теория: FAOSTAT за время работы над проектом несколько раз
лежал целиком (у них самих 521 от Cloudflare), и без резервного источника
годовой контур просто не собрался бы.

**Слои хранения.** `raw` — ответ источника как есть, JSON. `staging` —
разобрано по колонкам, с типами и общей сеткой (поле × дата или год).
`curated` — витрины, из которых читают модели и дашборды.

**Контроль качества.** Все семь типов из методички: полнота, уникальность,
допустимость значений, соответствие типов, диапазоны, ссылочная целостность,
актуальность. Результаты — в `quality_check_log`. Строка, не прошедшая
проверку диапазона, не идёт в витрину, но и не пропадает — уходит в таблицу
`quarantine` вместе с причиной.

**Происхождение показателей.** Таблица `lineage_log` плюс скрипт `lineage.py`.
`python lineage.py --field KRD-001` или `--year 2020` разворачивает цепочку от
дашборда до сырого ответа API одной командой — без этого пришлось бы
рассказывать словами на защите.

**История изменений.** `national_yield_revisions` пишется только добавлением.
Официальная статистика урожайности периодически пересматривается задним
числом, и после нескольких запусков в разные дни в этой таблице видно, что
именно изменилось.

**Дашборды и модели.** Два дашборда (предметный и операционный) в одном html,
каждый элемент отвечает на конкретный вопрос — см. `dashboard_export.py`.
Модели — минимум две с осмысленной абляцией, без утечек между обучением
и контролем (leave-one-field-out на полях, leave-one-year-out на годовом
контуре).

## Тесты

```bash
python -m pytest
```

59 тестов. Самые ценные — не те, что проверяют форму данных, а те, что ловят
утечку в валидации: перехватывают вызов `fit()` и проверяют, что тестовая
единица (поле или год) не попала в обучающую выборку. Такая ошибка не видна
по коду и не роняет программу — метрики просто становятся неправдоподобно
хорошими, и заметить её иначе, чем таким тестом, сложно.

## Что не доведено до конца, и почему

- **NDVI синтетический.** Для реального Sentinel-2 нужна OAuth-регистрация
  в Copernicus Data Space — код запроса написан (`sentinel2.fetch_real`), но
  не проверен вживую, регистрация не пройдена.
- **Урожайность в контуре по полям — формула, не факт.** Открытых данных
  по отдельным полям не существует в принципе; для содержательных выводов
  используется годовой контур, где урожайность настоящая.
- **Погода для годового контура — одна точка на всю страну.** Точный
  пространственно взвешенный расчёт по регионам потребовал бы данных
  о структуре посевных площадей, это за рамками проекта; в отчёте это
  ограничение отдельно оговорено.
- **Статус источников важен для интерпретации.** В сохранённом учебном запуске
  годовой целевой ряд может быть синтетическим при недоступности FAOSTAT/World Bank.
  В отчёте этот статус указан рядом с результатами, а повторный live-запуск
  не требует изменения кода модели.
